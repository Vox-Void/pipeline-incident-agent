# Data Pipeline Incident Agent

Imagine you are on call. Two payments came in, but the daily captured amount still reads ZAR 39.75. Did the writer stop before saving the rows, or did it save them and stop before updating the delivery record? This project lets you check what happened, see which reports depend on the delivery and approve a replay when the evidence supports it.

## How it was built

The project starts with small batches of fictional payments. Each batch is a JSON Lines file, with one payment revision per line. A seal records the file checksum, line count and a fingerprint of its lines. Spark saves the raw lines in Bronze, a Delta table. A second Delta table, Silver, holds validated payment revisions. SQLite keeps the delivery status, write attempts and approvals. When a writer stops after committing to Delta, the ledger can still show an unfinished attempt. The recovery code checks both records.

The producer's revision number determines which payment is current. A file can arrive late, so arrival time would put an older revision back on top. A payment also keeps its original merchant and business date across revisions. The accepted amount goes into an exact decimal column so the daily report can add values such as `4.25` without floating-point rounding. [Payment revision decision](decisions/001-payment-revisions.md)

The investigator and replay operator have separate jobs. The investigator reads a few named sources and can recommend an action. The operator reviews and approves a specific plan with its own fingerprint, called a digest. A new write can change the table after a plan is created, so the operator checks the plan again just before applying it. [Recovery decision](decisions/002-recovery-boundary.md)

The Docker image installs the locked Python dependencies, Java and the Delta connectors. Compose gives Spark and SQLite a named volume and saves reports to the checkout's `artifacts/` directory. The default container has its network disabled. Live OpenAI mode uses a separate Compose file. ## Follow a failed delivery

Run `./scripts/dev demo --scenario S04` after bootstrapping the image. You can also read the saved JSON report alongside these steps. The report shows the delivery, its write attempts and the investigator's evidence in one place. [Setup commands](../README.md#run-it) · [S04 report](example-results/s04.json)

1. **Start at ZAR 39.75.** The demo loads three payments under `BASELINE`. It then stages a two-row delivery called `RECOVERY`. Staging records its seal and moves the completed file into the watched inbox. The Spark stream appends each raw line to Bronze with its delivery ID and uses a checkpoint to track files it has read. [Demo inputs](../src/pipeline_incident/fixtures.py) · [Staging code](../src/pipeline_incident/deliveries.py) · [Spark capture](../src/pipeline_incident/spark_engine.py)
2. **Check the rows and stop before the write.** The projector compares the inbox file and Bronze rows with the seal. It validates each line against the producer's declared contract and checks for conflicts with earlier revisions. The demo injects a failure just before the Delta `MERGE`. The ledger holds an unfinished attempt. Reconciliation checks Delta and finds the table at the same version with no matching commit. It marks the attempt `FAILED_REPLAYABLE`. [Payment validation](../src/pipeline_incident/contracts.py) · [Delivery checks](../src/pipeline_incident/projection.py) · [Write and recovery code](../src/pipeline_incident/operations.py)
3. **Read the evidence.** The scripted investigator checks delivery status, contract findings and the list of downstream tables and views. It previews the two rows that replay would insert. The proposed diagnosis is `PRE_COMMIT_FAILURE`, with a recommendation to request an approved replay. Each evidence record has an ID in the report. The same verifier checks proposals from the live model and withholds a replay recommendation if required evidence is missing. [Evidence tools](../src/pipeline_incident/evidence.py) · [Investigator](../src/pipeline_incident/agent.py) · [Lineage](../contracts/lineage.json)
4. **Approve the plan and reach ZAR 76.75.** The plan records the delivery seal, the Silver version, the two candidate rows' digest and the estimated new balance. The demo first tries `apply` and gets `APPROVAL_REQUIRED`. Its fixture operator then approves that exact plan digest. A second `apply` rechecks the plan and inserts the two missing revisions. The current-payment view takes the highest revision per payment ID, so the daily totals keep one current row per payment. Running `apply` again returns the original operation ID. [Operator commands](../src/pipeline_incident/cli.py) · [Approval and apply](../src/pipeline_incident/operations.py) · [Views and totals](../src/pipeline_incident/spark_engine.py)

## What if the rows were already saved?

SQLite and Delta finish their writes separately. Before merging, the writer saves the operation ID, starting Silver version and expected row hashes in SQLite. The merge attaches its operation metadata to the Delta commit. If the worker dies after that commit, the next writer searches Delta history and checks the rows at the matching version. With an exact match, it finishes the existing ledger entry without another merge. If the version or rows leave doubt about what happened, it marks the attempt `NEEDS_RECONCILIATION` and stops further writes. ## Reading the tests

The scenario runner creates a fresh workspace for each case. In S03, the producer sends `amount_cents` where the schema requires `amount`. That batch stays in Bronze. A corrected delivery gets its own ID and reaches Silver. S08 takes away the lineage evidence and checks that the investigator asks for help. The evaluator runs the same cases with the fixed runbook and the scripted investigator, then compares their decisions with expected causes, actions and downstream views.
